# Chrome blocking and local privacy constraints

Research date: 2026-11-19. Supports [Establish Chrome blocking and local privacy constraints](https://github.com/mueller-k/stoic-block/issues/2). This is planning research, not an implemented or browser-tested extension.

## Documented platform facts

- Declarative Net Request (DNR) supports redirects, including `extensionPath`, with host permission. Dynamic rules survive restarts/upgrades. `requestDomains` includes subdomains and requires ASCII/punycode. `main_frame` targets top-level requests. Redirect rules count against the 5,000 unsafe dynamic-rule limit, not the 30,000 safe-rule allowance. Regex rules have additional limits. `updateDynamicRules` atomically replaces rules or rejects without changing them. `getDynamicRules` reads installed rules; `testMatchOutcome` tests hypothetical requests in unpacked extensions. DNR covers HTTP-cache responses, but not responses generated by website service workers or retrieved from their CacheStorage. Other extensions can affect outcomes. See the [DNR reference](https://developer.chrome.com/docs/extensions/reference/api/declarativeNetRequest).
- Ordinary Manifest V3 extensions cannot use blocking `webRequest` listeners; policy-installed extensions are an exception. See [webRequest](https://developer.chrome.com/docs/extensions/reference/api/webRequest).
- Navigation to an extension resource requires declaring it web accessible. Exposed files can also be fetched by matching origins; exposure therefore allows detection of the extension. Limit exposure to the quote page and necessary public assets, never settings/configuration. `use_dynamic_url` rotates resource identifiers per session, but compatibility with the selected redirect technique needs verification. See [web-accessible resources](https://developer.chrome.com/docs/extensions/reference/manifest/web-accessible-resources).
- `storage.local` requires `storage`, has a 10 MB quota, and is removed on uninstall. `storage.sync` synchronizes settings; do not use it. Local storage access can be restricted to trusted extension contexts using `setAccessLevel`. See [storage](https://developer.chrome.com/docs/extensions/reference/api/storage).
- Incognito requires user enablement. A package page cannot load as the main frame using the default spanning mode. Split mode supports separate execution but shares `storage.local` settings with regular mode; `not_allowed` explicitly excludes incognito. See [incognito](https://developer.chrome.com/docs/extensions/reference/manifest/incognito) and [permission declaration](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions).
- Host permission patterns use schemes and hosts; `*` as a scheme means HTTP and HTTPS. Paths in host permissions are ignored. See [match patterns](https://developer.chrome.com/docs/extensions/develop/concepts/match-patterns).
- Extension workers can terminate when idle. Persistent configuration must not depend on worker globals. See [worker lifecycle](https://developer.chrome.com/docs/extensions/develop/concepts/service-workers/lifecycle).
- Chrome's default extension CSP restricts scripts and objects, rather than forbidding all networking. A stricter custom policy is supported. See [extension CSP](https://developer.chrome.com/docs/extensions/reference/manifest/content-security-policy).
- The [WHATWG URL Standard](https://url.spec.whatwg.org/) defines parsing and IDNA conversion. Parsing accepts some unusual inputs, including nonstandard IPv4 spellings; successful parsing alone is not a product-level domain validator.

## Recommended architecture, pending maintainer decision

Use Manifest V3, `chrome.*` APIs, DNR dynamic rules, a small settings worker, `storage.local`, and bundled HTML/CSS/JS/quotes. Propose Chrome 121 as a conservative minimum; decide the actual supported floor during specification. No content scripts or per-visit callbacks are needed for the baseline. Avoid `tabs`, `history`, `webNavigation`, `webRequest`, `scripting`, `unlimitedStorage`, and production feedback permissions unless a later decision establishes a specific need.

Request `declarativeNetRequestWithHostAccess` and `storage`. Choose between upfront HTTP/HTTPS host access and optional per-site grants. The former offers predictable configuration with a broad warning; the latter minimizes granted access but introduces grant denial, revocation, and more settings interactions. Broad host access is a capability, not evidence of collecting browsing data. Explain its purpose accurately.

Compile each canonical domain into a deterministic redirect rule constrained to HTTP/HTTPS and top-level requests, targeting a constant `/quote.html`. A simple one-rule-per-domain design makes the user cap at most 5,000 entries, potentially fewer if extra rules are needed. Choose and test a smaller explicit product cap. An empty list must produce no rules, never a rule with its domain restriction omitted.

Do not embed the original address, domain, timestamp, or visit identifier in the quote URL, messages, logs, or storage. Pick quotes in page memory. Reloading a quote page can pick another quote, without reconstructing the blocked visit. Do not treat a web-accessible page as authenticated: it must ignore arbitrary query/hash input and offer no privileged settings operations or open-ended message handlers.

Use packaged assets and system fonts; no remote fonts, analytics, crash reporting, remote quote downloads, preconnects, or CDN dependencies. Propose CSP with `default-src 'self'`, `script-src 'self'`, `style-src 'self'`, `connect-src 'none'`, `object-src 'none'`, `frame-src 'none'`, `form-action 'none'`, and only necessary image/font sources. Audit generated output as well as source. CSP is defense in depth, not proof that code cannot initiate external navigations or use other browser APIs.

Phrase the privacy promise as no extension-originated external requests and no extension activity records. It does not mean Chrome makes no requests: installation/update checks, browser services, and ordinary browsing are separate. Installed DNR rules necessarily duplicate blocklist information as operational browser-managed configuration; disclose that distinction from visit records.

## Domain input policy proposed for discussion

Accept hostnames only in the first release, with examples beside the field. Trim outer whitespace, lowercase and convert internationalized hostnames to ASCII through the browser URL parser, then validate hostname syntax explicitly. Deduplicate canonical names. Preserve `www` and entered subdomains: `news.example.com` must not silently become `example.com`. No DNS lookup or network-based validation.

Reject schemes, paths, ports, credentials, query strings, fragments, wildcard syntax, blank labels, malformed names, IP literals, localhost, and single-label names unless the maintainer intentionally extends scope. Decide whether a trailing dot is rejected or canonicalized; test dotted navigation separately because settings normalization alone cannot guarantee request matching. Display canonicalized output before saving to avoid surprising broadening.

Decide whether public suffixes such as `com` and `co.uk` are rejected. Reliable suffix validation needs a bundled, maintained public-suffix dataset, not a live request or a naive last-two-label rule. Multi-tenant hosts are an additional reason not to infer a registrable domain automatically.

Boundary fixtures: `example.com` and `a.example.com` should match; `notexample.com`, `example.com.evil.test`, and an unrelated URL containing `example.com` in its path/query should not. Cover mixed case, Unicode/punycode, explicit/default ports, trailing dots, duplicates, parent/child overlap, and invalid percent-encoded/credential-bearing input.

## Navigation and failure boundaries

The baseline intentionally leaves already-loaded pages alone. New network navigations/reloads are the interception point. Same-document history changes and fragments do not establish a fresh interception opportunity. Back/forward restoration, prerendered pages, offline service-worker pages, and POST navigations require explicit browser acceptance tests; do not promise that every visually apparent visit always becomes a quote.

Restrict supported browsing to ordinary HTTP/HTTPS pages. Browser UI (`chrome://`), extension pages, `file:`, `data:`, `about:`, and protected Chrome surfaces are outside the proposed contract. Verify Chrome Web Store handling rather than promising it is blockable. Blocking is a focus aid: users can disable/uninstall the extension or withhold host/incognito access.

Serialize settings mutations. Apply a full rule replacement in one API operation, await completion, then verify installed state before reporting success. Storage and rules are separate APIs, so there is no documented cross-API transaction. Use a bounded pending-settings record containing configuration only, and recover/reconcile after worker termination or restart. A failed save must remain visibly failed, including when old blocking remains active. Never report global disable or site removal as successful before enforcement agrees. Define which configuration is authoritative and how pending changes are retried or rolled back before implementation.

On rule rejection, keep the previous effective configuration and show a specific recoverable error. On denied/revoked host access, show that coverage is incomplete. On unavailable storage, don't silently reset the blocklist. On corrupt stored configuration, validate before applying anything and explain recovery. Avoid loops by matching only external HTTP/HTTPS destinations. Concurrent regular/incognito editors need one conflict policy if split mode is supported.

## Verification required before release

These are proposed acceptance checks, not completed tests:

1. Pure normalization/compiler tests for the boundary fixtures above, empty lists, overlaps, stable rule IDs, and the chosen cap.
2. Unpacked-extension rule matching checks, then actual Chrome navigation tests with host grants present/absent/revoked. A hypothetical match alone does not prove a redirect renders.
3. Real top-level address-bar, link, reload, new-tab, server-redirect and POST cases; negative iframe/subresource cases; existing tabs unchanged. Test HTTP cache, website service workers/CacheStorage, SPA changes, history restoration, dotted/IDN hosts and protected pages. Document observed limitations by browser version.
4. Restart, upgrade and worker termination; concurrent saves; rejected rule updates; quota/storage failures and termination between storage/rule writes. Check effective state after recovery and success/error messages, especially disable/remove.
5. If incognito is supported, test user enablement, split rendering, shared configuration and concurrent edits. Otherwise verify incognito exclusion is explicit.
6. Inspect release archive, manifest, dependencies, CSP and every network-capable API. Capture traffic for worker, settings and quote contexts across install/configure/redirect/reload/restart/offline use. Confirm zero extension-originated external traffic and absence of visit data in storage/logs. Keep test captures outside the distributed extension; isolate browser update/service traffic in the evidence.
7. Run the packaged release build on the selected minimum and current stable Chrome, with another redirect/blocking extension enabled as an interference case. Record exact versions and results.

## Decisions for the existing release-specification ticket

[Settle the implementation-ready release specification](https://github.com/mueller-k/stoic-block/issues/5) should settle:

- Accept DNR's network-stack coverage boundary, or investigate broader navigation handling before promising universal replacement? Broader handling could require new permissions, callbacks and privacy analysis.
- Upfront versus optional host grants, minimum Chrome version, and blocklist cap.
- Hostname-only input versus pasted URLs; IP/local-host/public-suffix policy; trailing dots; normalization confirmation.
- Incognito excluded or user-enabled split mode; configuration-write conflict behavior if split.
- Cross-API recovery authority, visible failure states, and precise privacy/permission wording.
- Meaning of a blocked visit for random quote selection across reload/history restoration.

These are unresolved product choices, not decisions made by this research. They already fit the existing specification ticket, so no duplicate decision ticket is needed.
